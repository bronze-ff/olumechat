# PORTE — de fork on-prem a SaaS multi-tenant

Este repo nasceu como fork do `mc-atendimentos` (single-tenant, Oracle, on-prem,
acoplado ao ERP WinThor). O acoplamento com o cliente original já saiu. O que
falta para virar **Falatta** está aqui, em ordem de dependência.

**Nada disso é opcional para vender o produto.** Enquanto estes itens não
fecharem, o repo não roda em produção.

---

## Onda 1 — fundação (bloqueia todo o resto)

### 1.1 Porte Oracle → PostgreSQL (Neon)

O maior item. Superfície medida no fork: **~244 chamadas `conn.execute`** em
**119 arquivos** de server.

O que muda:

| Oracle | Postgres |
|---|---|
| binds `:nome` | `$1, $2...` (ou `pg` com named via wrapper) |
| `GENERATED BY DEFAULT AS IDENTITY` | `GENERATED ALWAYS AS IDENTITY` / `bigserial` |
| `RETURNING ... INTO` | `RETURNING` direto |
| `SYSTIMESTAMP` | `now()` |
| `FETCH FIRST n ROWS ONLY` | `LIMIT n` (ou mantém — PG 8.4+ aceita) |
| `IS JSON` / CLOB de JSON | `jsonb` |
| `NVL` | `COALESCE` |
| `node-oracledb` thick + Instant Client | `pg` (sem binário nativo) |

**Ganho colateral:** o charset `WE8MSWIN1252` some. Postgres é UTF-8, então o
workaround de codificar codepoints > 0xFF (`utils/texto.js`, usado em **14
arquivos**) pode ser **deletado**, não portado. Emoji passa a funcionar nativo.

DDL original de referência em `docs/referencia/schema-oracle/` — 17 tabelas.

### 1.2 Multi-tenancy: `tenant_id` + RLS

Modelo escolhido: **shared schema + Row-Level Security**. Schema-per-tenant
sofre em migração e incha o `pg_catalog` acima de algumas centenas de tenants.

- `tenant_id` em **todas** as tabelas, com índice como primeira coluna dos
  índices compostos existentes.
- `ENABLE ROW LEVEL SECURITY` + policy por tabela.
- ⚠️ **Armadilha crítica:** o pooler do Neon roda PgBouncer em *transaction
  mode*. O tenant DEVE ser setado com
  `set_config('app.current_tenant_id', $1, true)` — o `true` final o torna
  **transaction-scoped**. Usar `SET SESSION` vaza o tenant entre requisições na
  conexão pooled: uma farmácia veria dado de outra. Isto precisa de teste
  automatizado dedicado.

### 1.3 Login próprio

`auth/routes.js` ainda autentica contra a tabela de senhas do ERP do cliente
original. Substituir por tabela de usuários própria, com hash (argon2/bcrypt),
escopada por tenant. O RBAC (`auth/rbac.js`), o JWT e a blacklist de `jti`
ficam como estão.

### 1.4 Renomear o schema

`MC_ZAP_*` → prefixo do produto. Fazer **junto** com o porte de SQL (1.1), não
depois — é o mesmo conjunto de queries.

## Onda 2 — escalar horizontalmente

A v1 declarava como decisão de projeto: *"Sem Redis. Workers são in-process."*
Isso era **correto** para um servidor único on-prem e **quebra** com 2+
instâncias. Precisa ser resolvido antes de escalar.

| Componente | Hoje | Problema com N instâncias |
|---|---|---|
| `realtime/hub.js` | `EventEmitter` local | mensagem que chega na instância A não aparece no SSE de quem está na B |
| `fila/distribuidor` | `setInterval` in-process | N instâncias distribuem a mesma conversa |
| `bot/sweeper` | `setInterval` in-process | timeout disparado N vezes |
| `campanha/dispatcher` | `setInterval` in-process | **mensagem duplicada pro cliente final, cobrada pela Meta** |
| `utils/tokenBlacklist` | `Set` em memória | logout não propaga entre instâncias |

Caminhos:

- **Barramento:** Postgres `LISTEN/NOTIFY` — mas ⚠️ **não funciona** no pooler
  em transaction mode; exige conexão direta (session mode). Alternativa: Redis.
- **Workers:** eleição por `pg_advisory_xact_lock` (só uma instância roda o
  tick) — funciona no pooler e não adiciona dependência.
- **Blacklist:** move para tabela com TTL, ou Redis.

## Onda 3 — o que o SaaS exige e o fork não tem

### 3.1 Painel do operador (super-admin)

Fora do RBAC do tenant. Libera acesso a novos clientes, provisiona tenant,
acompanha uso/licença. Hoje não existe — o RBAC atual só conhece papéis
*dentro* de uma empresa.

### 3.2 Onboarding Meta via Embedded Signup

O cliente final não consegue fazer o processo da Meta sozinho. A solução
oficial é o **Tech Provider Program + Embedded Signup**: popup da Meta dentro
do nosso painel, o cliente loga no Facebook dele, autoriza, a WABA dele é
criada e recebemos o token programaticamente.

- Exige registro como Tech Provider junto à Meta.
- O painel do operador (3.1) continua como fallback manual.
- Hoje o token da Meta vem do `.env` — passa a ser **por tenant, no banco,
  cifrado** (reusar `ia/crypto.js`, que já faz AES-256-GCM).

### 3.3 Hospedagem

SSE e workers de longa duração **eliminam serverless puro** (Vercel/Lambda dão
timeout). Precisa de container persistente: Fly.io, Render, Railway ou VPS.

### 3.4 Armazenamento de mídia

Hoje a mídia vai pro disco local (`MEDIA_DIR`). Em container efêmero isso se
perde. Precisa de object storage (S3/R2).

## Resíduo conhecido do fork

Coisas que ficaram e devem sumir junto com a onda em que se encaixam:

- `utils/clienteLookup.js` — já é um seam no-op, mas a função ainda se chama
  `dadosClienteWinthor`. Renomear para `dadosDoCliente` junto com os 4 call
  sites (`webhook/processEvent.js`, `api/contatos.js`, `api/conversas.js`).
- `api/contatos.js` — ainda carrega os campos de vínculo com o cadastro de
  cliente do ERP antigo (`CODCLI`/`CGCENT`). Generalizar para
  `codigo_externo`/`documento`.
- `campanha/segmento.js` — segmento é um SELECT livre escrito por admin. Num
  SaaS multi-tenant isso é **perigoso** (SELECT arbitrário no banco
  compartilhado). Substituir por import de CSV + segmentação por atributo de
  contato. **Bloqueia o go-live.**
- `bot` nó `consulta` — mesma questão do item acima: SQL livre por tenant.
  Reavaliar sob RLS.
- `server/public/exclusao-de-dados.html` — página exigida pela Meta, ainda com
  a marca do cliente original. Regerar por tenant.
- `.env.example` — ainda descreve variáveis single-tenant.
- **Identidade visual** — os arquivos de marca do cliente original foram
  removidos, mas `client/public/favicon*.{svg,png}`, `apple-touch-icon.png` e
  `icon-{192,512}.png` **ainda são a arte antiga**. Precisam ser refeitos com a
  identidade do Falatta (estão referenciados no `index.html` e no manifest, então
  não podem só ser deletados). A paleta no `tailwind.config.js` também é a do
  cliente original.
- `server/telemetria/pulso-agent.js` — heartbeat de licença/uso que "liga pra
  casa". É genérico (URL vem de `PULSO_URL`) e não vaza nada do cliente antigo,
  mas num SaaS hospedado por nós é redundante: já temos os dados. Decidir se
  vira métrica interna ou sai.
